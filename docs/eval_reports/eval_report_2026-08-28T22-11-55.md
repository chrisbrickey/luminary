### II. Scores for `retrieval_relevance` hit an artificial ceiling below threshold

The `retrieval_relevance` score of `0.50` (stable between the old and new machine) is an F1 score, considering the chunks the judge expected and the chunks the retriever returned.

There are two configurations that are currently problematic and that heavily influence the F1 calculation. The current values of these two settings made it impossible for most `retrieval_relevance` examples to achieve threshold.
- The chat chain always retrieves `DEFAULT_K` chunks, currently set to 10. This number is the denominator in the precision calculation.
- The golden dataset v3.6 includes 5-7 expected chunks per example. _This figure is influenced by the LLM-as-judge mechanism that generates golden datasets and currently requests 3-7 chunks per example._

Precision is capped at `expected_count / 10` even when every expected chunk is found. So the best possible F1 score is `2 * expected_count / (10 + expected_count)`.
The table below illustrates the mathematical ceiling for the entire range of current possibilities in a golden dataset.

| expected chunks | max precision | max F1 | can reach 0.80 threshold? | examples with this count in `v3.6` |
|----------------:|--------------:|-------:|---------------------------|-----------------------------------:|
|               3 |          0.30 |   0.46 | no                        |                                  0 |
|               4 |          0.40 |   0.57 | no                        |                                  0 |
|               5 |          0.50 |   0.67 | no                        |                                  4 |
|               6 |          0.60 |   0.75 | no                        |                                  3 |
|               7 |          0.70 |   0.82 | only at perfect recall    |                                  3 |

Looking at the table above, we can see that only three golden examples in the `v3.6` dataset (the ones with 7 expected chunks) could have achieved the 0.8 threshold mathematically.
But in order to achieve that threshold, those examples would have had to have perfect recall, which none of them had.
So the pass rate was being driven more by arithmetic than by retrieval quality - though both contributed to the score.
The issue here is that pass/fail and score variations between runs on `retrieval_relevance` carried much less actionable information than expected.

## Changes Made

### Replaced the F1 score in `retrieval_relevance` metric with recall@K

**Approach:**

I changed the reported score for `retrieval_relevance` in `src/eval/metrics/retrieval.py` from F1 (harmonic mean of recall and set precision)
to recall@K: of the expected chunks (N), the fraction that appear anywhere in the chunks that the retriever returned (K).
Recall@K does not have a false ceiling. It reaches 1.0 whenever every expected chunk is somewhere in the retrieved set, regardless of the number of chunks requested by the chat chain.

In addition to the reported recall@K score, other calculations were added to the eval artifacts (`MetricResult.details`) for audit purposes only. These do not contribute to the reported score or pass/fail for the metric.
- **nDCG@K:** Shows whether the expected chunks landed near the top of the retrieved list, which is what the model reads first.; Discounts each found chunk by the log of its rank and normalizes against the ideal ordering. The ideal places `min(n, K)` expected chunks in the top slots.
- **precision@N:** Keeps a precision signal without penalizing the retriever for returning the specified number of chunks that the chat chain requested.; Measured over the top N results, where N is the expected retrieved chunk count.
- **F1:** legacy score; retained to compare against eval artifacts generated before the metric was updated

A subsequent eval cycle was triggered after the code change was finalized: `2026-08-28T22-07-25.json`. No other changes were made.

**Hypothesis:**

`retrieval_relevance` scores should rise uniformly without any change to the actual chunks that are retrieved because the K penalty has been removed.
The size of the diff per example should be roughly the size of the K penalty that the old formula applied, which was largest for examples with fewer expected chunks.

The metric should become informative going forward:
- The 0.80 threshold becomes reachable for every example rather than for only the three with 7 expected chunks. So pass/fail starts reflecting retrieval quality instead of arithmetic.
- A perfect 1.0 becomes attainable on real run data.
- Subsequent movement in this metric should be readable as a change in the retriever, the corpus, the chunking, or the embedding model.

**Findings from eval artifact `2026-08-28T22-07-25.json`:**

As expected:
- The only metric with a score change was `retrieval_relevance`. All other scores remained identical to the previous run.
- The actual chunks retrieved were also identical to the previous run. So the difference in score was due entirely to the change in how the score was calculated.
- The reported score is now recall@K: the share of expected chunks found anywhere in the retrieved set. Recall is no longer capped by the gap between the retrieved and expected counts.
- The shift in score was largest for golden examples with the fewest expected chunks, which were impacted the most by the K penalty of the old F1 score.

Scoring highlights:
- The overall aggregate score increased from 0.5 (F1) to 0.68 (recall@K), which is still below the 0.8 threshold.

- The language gap remains: recall@K was 0.72 (en) and 0.64 (fr). The old F1 was 0.54 (en) and 0.46 (fr).

## Changes Deferred

### Control for variability between machines

Within a machine, the pipeline is byte-identical over many days, many eval runs, and across a full corpus re-index.
Across machines, performance is stable except for specific word choice. The LLM-generated responses use very different word choice.
Cross-machine determinism was never a property of the eval harness, but now we have a measurement of it and there are multiple contributing factors that could be addressed if greater control is desired.

The below variables are ranked by how likely each is to explain the variation observed between the machines, which manifested in a decline of the `keyword_coverage` metric.

1. Model weights behind the `:latest` tags.
The new run records `mistral:latest` at digest `6577803aa9a0` and `bge-m3:latest` at digest `790764642607`; `ollama list` shows both pulled roughly eleven days before the run.
The old run recorded no digest at all, because the `ollama_loaded_models` field did not exist yet in that artifact. `:latest` is a moving tag, so a re-pull on the new machine can deliver different weights, a different quantization, or a different chat template under the same name.
This is the strongest candidate for a generation shift and is currently unverifiable, since the old digest was never persisted.

2. Ollama version.
The new run records `0.33.1`. The old run records nothing.
Ollama releases change sampler implementations, chat templating, default context length, and GPU kernels, any of which changes greedy decoding output without touching the embedding results in a visible way.

3. Hardware.
Different silicon means different kernels and a different reduction order in floating point accumulation.
Even with byte-identical weights, this flips near-ties. The two adjacent retrieval swaps are precisely this effect showing up in the one place where it is observable, and the same effect at the logit level is enough to change greedy token selection and cascade into different wording.

4. VRAM residency and layer offload.
The new run shows both models fully resident in VRAM (`size_vram` equals `size` for both).
If the old machine had less VRAM and offloaded layers to CPU, part of the forward pass ran in a different precision and a different kernel. Old-machine residency was never recorded.

5. Context length.
The new snapshot records `context_length` 32768 for mistral and 8192 for bge-m3.
The old snapshot records neither, so a change in the default context window cannot be ruled out.

6. Ollama client/server version skew.
On the new machine `ollama --version` reports server 0.33.1 with a warning that the client is 0.32.14.
This is worth resolving so the recorded version is unambiguous.
