### Metric ceiling: `retrieval_relevance` cannot pass at K=10

`retrieval_relevance` is set-F1 between the judge-selected `expected_chunk_ids` and the retriever's top-K.
Two constraints are fixed independently of retrieval quality:

- The golden-dataset prompts (both `dataset_generation.py` and `rechunk.py`) instruct the LLM judge to select 3-7 chunks, so the expected count per example is between 3 and 7.
- `DEFAULT_K = 10`, so exactly 10 chunks are retrieved for every example.

Precision is therefore capped at `expected_count / 10` even when every expected chunk is retrieved.
Max achievable F1 given perfect recall is `2 * expected_count / (10 + expected_count)`:

| expected count | max precision | max F1 | can reach the 0.80 threshold? |
|---------------:|--------------:|-------:|-------------------------------|
|              3 |          0.30 |   0.46 | no                            |
|              4 |          0.40 |   0.57 | no                            |
|              5 |          0.50 |   0.67 | no                            |
|              6 |          0.60 |   0.75 | no                            |
|              7 |          0.70 |   0.82 | only at recall 1.00           |

Measured over all 59 scored example-trials in the chunk size experiments below (10 examples x 6 trials, minus the one skipped example):

| expected count | max F1 | example-trials | share |
|---------------:|-------:|---------------:|------:|
|              3 |   0.46 |              1 |    2% |
|              4 |   0.57 |              1 |    2% |
|              5 |   0.67 |             25 |   42% |
|              6 |   0.75 |             15 |   25% |
|              7 |   0.82 |             17 |   29% |

- 42 of 59 example-trials (71%) could not reach 0.80 no matter what the retriever returned.
- The remaining 17 could reach 0.82, but only at perfect recall. None of them achieved perfect recall.
- Three example-trials did achieve perfect recall (every expected chunk was retrieved) and still scored as failures: `tolerance_en` at chunk size 600 (0.67), `science_moral_progress_en` at 1200 (0.75), and `judicial_torture_fr` at 1600 (0.67).

Aggregated per trial, the arithmetic maximum sits below the threshold in every case:

|-----------------|--------------------:|----------------------------:|--------------------:|------------:|
| 600             |                 5.9 |                        0.74 |                0.50 |        0.68 |
| 800             |                 5.7 |                        0.72 |                0.48 |        0.66 |
| 1000            |                 5.5 |                        0.70 |                0.43 |        0.59 |
| 1200 (baseline) |                 5.9 |                        0.74 |                0.50 |        0.68 |
| 1400            |                 5.7 |                        0.72 |                0.46 |        0.63 |
| 1600            |                 6.0 |                        0.75 |                0.50 |        0.66 |

The 0.80 threshold is above the metric's own maximum (0.70-0.75) in all six trials. The pass rate of 0.00 was determined before the retriever ran.

Second-order effect: the expected count is chosen by the LLM judge per example per trial, so the ceiling itself moves between trials.
`judicial_torture_en` had a ceiling of 0.75 at chunk size 1200 (6 expected chunks) and 0.46 at chunk size 1000 (3 expected chunks).
Part of the per-example variance attributed to judge noise elsewhere in this report is ceiling movement rather than a change in retrieval quality.

Implications:
- No chunk size can fix this, and neither can K tuning on its own. Raising K lowers precision further. Lowering K toward the expected count would raise the ceiling but would starve the chat chain of context.
- F1 with a 0.80 threshold is the wrong formulation for an asymmetric setup where the retrieved count is fixed at 10 and the expected count is 3-7.
- Until the metric is fixed, `retrieval_relevance` scores are usable only for relative comparison between variants, and only when the expected count is stable. The pass/fail status is not usable at all.

See `Changes Deferred` for candidate fixes.

### Ollama state during eval run is masked

If Ollama is always restarted before an eval run, then the run is operating on a cold state. Eval runs on cold state have very little variation between them.
If Ollama is not restarted before an eval run, there is more variability among the warm-state runs.
During the first attempt at chunk size tuning (the experiments on 2026-07-13), Ollama was not restarted before each eval run and this variable was masked
because this characteristic of the eval run was not captured in the `SystemSnapshot`.

### Noise from LLM-judge when selecting expected chunks

The initial implementation of the rechunk workflow was a one-time CLI script paired with an extracted rechunker module. It ran a single LLM pass per golden example over a pool 15 chunk candidates. 
During the first attempt at chunk size tuning (the experiments on 2026-07-13), noise variation of ±0.05 was observed among all experiments.
That estimated error is not large enough to significantly impact the `retrieval_relevance` scores, but it would make it easier to evaluate experiments if that noise was reduced. 

Two occurrences especially suggest the need for improvement in this workflow.
- `judicial_torture_en` at chunk_size=1400: the judge returned `expected_chunk_ids=[]`, so the eval runner skipped `retrieval_relevance` for that example.
- `judicial_torture_en` at chunk_size=1000: the judge selected 5 chunks that had zero overlap with the retriever's top-10, dropping the example to F1=0.00.

## Changes Made

### Capture Ollama state in `SystemSnapshot` for traceability

Extended `SystemSnapshot` data structure with four optional string fields: `ollama_pid`, `ollama_uptime_seconds`, `ollama_version`, and `ollama_loaded_models`.
The fields are optional for backwards compatibility with previous eval artifacts.

- **PID:** process holding the listening socket
  - read via `lsof -nP -iTCP:11434 -sTCP:LISTEN -Fp`
  - PID plus uptime lets a reader confirm whether Ollama was restarted between runs. 
- **Uptime:** elapsed seconds
  - read via `ps -o etimes= -p <pid>`
- **Ollama version:** 
  - read via `GET /api/version` 
  - Version lets a reader correlate future behavior deltas to Ollama upgrades.
- **Loaded models:** JSON-serialized snapshot of models currently resident in VRAM with their keep-alive expiry
  - read via `GET /api/ps`
  - The loaded-models field captures the strongest warm-state signal by recording which model weights are already cache-primed at eval start. This is the mechanism behind the warm-state variance observed in the 2026-07-13 experiments.

Added a new helper function `capture_ollama_state()` that returns an `OllamaRuntimeState` Pydantic model. The helper does four best-effort lookups, each wrapped so any failure yields `None` for that field rather than raising.

Wired the helper into `get_system_snapshot()` in the eval runner. 

Updated `TEMPLATE.md` with bullets for the new fields so that they will be automatically included in future narrative eval reports.

#### Hypothesis refuted: Smaller chunks did not improve retrieval

I was working under the assumption that `retrieval_relevance` scores were low due to retrieved chunks containing too many themes. 
But these initial experiments (if reliable) invalidate that hypothesis because smaller chunk sizes (600, 800, 1000) resulted in lower individual scores than larger chunk sizes (1400 and 1600). 

Contributing mechanisms:
- The adjacency is semantic, not spatial. Voltaire's work, "Lettres philosophiques", groups closely related topics into consecutive letters: Quaker theology sits next to religious tolerance, Locke's epistemology sits next to Newton's physics. The vector index correctly returns Quaker etiquette for a tolerance query because the two spans are near each other in `bge-m3` embedding space, not because a chunk straddled a boundary. Cutting chunks does not separate content that the embedding model already considers similar.
- Smaller chunks embed to more ambiguous vectors. A 1200-character chunk carries enough context for its embedding to encode a specific argument. An 800- or 600-character chunk often carries only a topic label ("Locke", "Newton", "toleration"). Those shorter vectors end up being more thematically ambiguous and sitting closer to more query vectors. The result is that they win more retrieval slots across unrelated queries.
- More chunks means more competition for the top-10 (the K=10 chunks retrieved per query). At chunk size 1200 there are a little more than 200 chunks. At chunk size 600, there are roughly twice as many chunks. But K (number of chunks retrieved per query) stayed constant so every expected chunk faces more competition from thematically close neighbors as the chunk size decreases.
- Character-boundary splits do not respect argument boundaries. `RecursiveCharacterTextSplitter` targets a character count with separator fallbacks (`\n\n`, `\n`, `. `, ` `, `""`). At 600 characters the splitter lands mid-argument more often, so the resulting chunks are individually less coherent, further muddling their embeddings.

    
## Changes Deferred

### Fix the `retrieval_relevance` metric ceiling

The metric cannot reach its 0.80 threshold at K=10 with 3-7 expected chunks. See the `Metric ceiling` subsection under `Issues` for the full analysis.

Candidate fixes:
1. Replace plain set-F1 with recall@K plus a rank-aware metric (nDCG@10 or MRR).
  - Recall@K is unbounded by the expected/retrieved size mismatch and directly answers "did the retriever find the right passages".
  - A rank-aware metric captures whether the right chunks landed near the top, which is what actually matters to the downstream LLM.
2. Compute precision over the top-N retrieved where N is the expected count (precision@N) rather than over all 10.
  - Keeps a precision signal without penalizing the retriever for returning the 10 chunks the chat chain asked for.
3. Fix the expected count at a constant in the judge prompt (currently "3-7").
  - A variable expected count makes the ceiling move between trials, which injects noise that looks like a performance change.
4. Set the threshold from the achievable maximum, or normalize the score by it (`f1 / max_achievable_f1`).
  - Lowest-effort option, but it keeps the confusing property that a perfect retrieval scores 0.67.

Recommendation: 1 and 2 together, with 3 as a cheap accompanying change to the judge prompt.

### Reduce noise from LLM-judge when selecting expected chunks

Potential tactics to reduce noise:
1. Widen the candidate pool for the LLM judge.
  - Retrieve k=30+ (compared to k=15) chunks while still asking the LLM to pick 3-7. A wider pool reduces both empty-list catastrophic failures and the zero-overlap coverage gaps. 
  - Low-cost change: one integer in `regenerate_expected_chunk_ids`.
2. Implement multi-pass voting.
  - Run the judge 3 times per example (compared to 1 time) and take the intersection or majority vote. Smooths out single-shot randomness and adds a second guard against the empty-list failure. 
  - Higher cost change: 3x as many LLM calls per golden example.
3. Determine the noise floor for the LLM-as-judge when selecting expected chunks.
  - Use the LLM-as-judge process to construct multiple golden datasets at the baseline chunk size. 
  - Then run the eval against those different datasets.
  - The range of scores in the resulting eval artifacts indicates the 'error' due to the manner in which expected chunks are selected. Going forward, only score improvements beyond that delta should be considered real performance gains.
4. Log the top-k candidates. Add these to the golden dataset itself so that future analysts can audit both the retriever and the LLM judge.

Rationale for deferral: These changes would help to quantify and reduce the noise, but they are not likely to change the final outcome of the chunk size tuning experiments.

## Changes Rejected

### Tune `chunk_overlap`

- Increasing overlap makes chunks more redundant. In the worst case the top-10 could contain two near-copies of the same content, so one semantic hit only fills five chunks and the other five are still off-topic neighbors. This could hurt precision, not help it.
- Decreasing overlap sharpens separation but risks mid-argument splits, worsening chunk coherence.
- The 12.5% ratio chunk_overlap:chunk_size held constant across the experiments is already a reasonable default. 
- Running additional experiments that vary chunk_overlap (e.g., 0% / 12.5% / 25%) at chunk_size=1200 would likely move `retrieval_relevance` by less than the ±0.05 measurement noise already observed. So any real gains would not be distinguishable from the noise caused by LLM-as-judge when selecting the expected chunk ids.

Rationale for rejection: unlikely to move the needle; The role of the `chunk_overlap` variable is to keep an important sentence from being lost across a chunk boundary. This would not address the current root cause of low `retrieval_relevance` scores and would likely move scores less than the LLM-as-judge noise.
